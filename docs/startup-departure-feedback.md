# Startup waits for a real app departure

Starting a run now keeps its departure instruction and Cancel action visible until iOS actually backgrounds ESP32 Agent. The character's brief take-off animation can finish independently. If automatic departure does not work, the same screen tells the user to swipe Home and waits at most 30 seconds; it no longer disappears after 800 milliseconds.

The startup sequence tries three independent methods: the board's consumer Home key, Cmd+H, then a real home-bar flick. A successful board acknowledgement does not skip later methods unless iOS confirms the app is in the background. No private UIKit app-exit API is used.

All startup entry points share a cancellable task, including shortcuts and consent/recovery retries. Cancel stops startup before the planner begins, releases the pointer, closes the Live Activity, and records a stopped start rather than a failure notification. A lost board or slow command during startup immediately changes the instruction and Live Activity to connection guidance. A normal disconnect pauses startup for up to the existing five-minute recovery limit; moving the board closer and reconnecting automatically retries the same departure method. Stop remains available, and a notification is only needed after the normal quiet recovery interval.

Every accepted start selects the Agent tab so guidance and Cancel are visible even when a shortcut or consent retry began from Settings. Before the first planner frame, startup checks cancellation, board connectivity, and background state again, and validates capture time against the recorded iOS background notification (falling back to the pre-gesture request time). It waits at most three seconds for the stream before moving only the cursor and requesting an explicit snapshot. This creates a genuinely newer image on a static Home Screen without clicks or timestamp tolerances; a newly decoded but older buffered GOP is rejected and retried with visible recovery guidance. A connected mirroring session with no fresh image gets a distinct frame-wait status. A pure display monitor, driven by the existing app tick and BLE callbacks, immediately surfaces active-run disconnections even during a model request; it does not start another hardware recovery task. The run gate also treats an inactive foreground app as still visible, so a system overlay does not let the planner inspect ESP32 Agent's own screen.

Automated checks cover ineffective Home acknowledgements falling through to the physical swipe, command errors, lost connections, and cancellation before another attempt. Physical departure and weak-signal behavior still require an on-device run with the board attached.
